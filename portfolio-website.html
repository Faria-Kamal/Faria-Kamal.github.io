The brief

I needed one place that could do three jobs: explain who I am, show the work I can actually defend, and make it easy for a recruiter to contact me. The constraints were deliberate — free hosting, no paid domain yet, and no invented projects, metrics or employment outcomes.

That meant the content had to come from evidence I already had: my CV, the documented hotel cancellation project, the in-progress retail analysis, and the GitHub repositories that hold the code.

Design direction

The visual reference I was given had a simple vintage feel: low colour contrast, serif type, an elegant index tucked into the lower-left corner, and a small “now” section for what the owner was watching and reading. The reference URL is now a parked advertising page, so I worked from that description rather than copying a live layout.

After feedback, the palette moved from warm paper tones to a calmer, more sober scheme: soft grey-green paper, slate ink and a muted sage accent. The corner index became a small dashboard-style control panel with three summary tiles and seven section tiles. The final layer is narrative. The seven sections are introduced as chapters, the corner panel is a contents / scene selector, each case study opens with a scene mark and a running order, and a 3px hairline rail shows how far you are through the story. It is all typography and restraint rather than effect: reveals are slow, there is no autoplay, and every animation is disabled when the visitor asks for reduced motion.

Rule I kept coming back to: if a claim cannot be traced to the CV, a report or a results file, it does not go on the site.

Structure

The site is deliberately small and flat, which suits GitHub Pages and makes it easy to reason about:

  • index.html — one-page home with About, Toolkit, Work, Experience, Education, Now and Contact.
  • hotel-booking-cancellation.html — completed case study with verified metrics and limitations.
  • online-retail-customer-analysis.html — in-progress case study with no results invented.
  • portfolio-website.html — this page.
  • assets/css/style.css — all styling, driven by CSS variables.
  • assets/js/config.js — approved contact details in one editable place.
  • assets/js/main.js — menu, contact rendering and gentle scroll reveal.

The case studies sit at the root rather than in a nested folder so that relative asset paths resolve correctly in a plain static preview.

Mobile friendliness

The layout uses CSS Grid with two breakpoints. At 900px the hero, two-column sections, skills and contact panels collapse into a single column. At 600px the container narrows, type scales down, project cards drop their index number, and the dashboard menu becomes a single-column panel with smaller padding.

The fixed “+” menu stays reachable at the lower left on small screens, tile links are large enough to tap, and images are constrained with max-width: 100%. A skip link gives keyboard users a direct route to the main content.

Accessibility and testing

Colour choices were checked for contrast rather than picked by eye only. The palette uses a slate ink on cool paper, a darker sage for small labels, and a muted body text colour that still clears WCAG AA for normal text.

Each page was opened in Chromium and checked with Lighthouse: 100 Accessibility and 100 Best Practices, with no console errors. The corner menu was tested for click, Escape, outside-click and contact-link rendering. Motion is reduced automatically when the visitor's system asks for reduced motion.

Publishing workflow

This repository is being built one page at a time. Each meaningful change becomes a commit with a short message, then gets pushed to GitHub. That gives a clear history: you can see the first home page, the case studies, the design refinement, and the final deployment setup as separate steps rather than one opaque upload.

The plan is to push a first working version, enable GitHub Pages from the main branch, confirm the live URL, then continue improving it in small commits.

Target: https://Faria-Kamal.github.io/ · repository link will be added after the first push.

What this taught me

The useful lesson was that design and evidence are the same conversation. Deciding what not to claim made the site stronger. So did treating accessibility as a design constraint from the start, and keeping the deploy path simple enough that the site can be maintained without a build pipeline.

The Git workflow is part of the project too: small commits, clear messages and the ability to pull the latest changes before starting new work.
